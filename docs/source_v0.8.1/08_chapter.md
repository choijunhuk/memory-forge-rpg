# <a id="ch8"></a>8. 기억 저장: 현재 참조와 보존형 v2 목표

> **현재와 목표를 구분한다.** §8.1~8.7은 현재 Run/HTML의 legacy 동작과 비용표다. 실제 제작 목표는 §8.8~8.14이며 기존 덱 보존·최종 용량 검사가 핵심이다. 연결 완료 전 두 정책을 섞지 않는다.

## 8.1 개념

- 캐릭터마다 **기억 덱**이 1개 있다. 처음에는 기본 덱(그 캐릭터의 시작 카드 4장 + 지정 공용 카드 1장).
- 탐사가 끝나면 이번 탐사 덱이 기본 덱과 **어떻게 달라졌는지**를 변경 목록으로 보여 주고, 캐릭터별 **기억 용량** 안에서 남길 변경을 고른다. 고른 변경만 반영한 덱이 새 기억 덱이 된다(이전 기억 덱은 이력으로 보관).
- 기억 덱은 다음 탐사의 시작 덱이며, 주간 보스·기록 균열·성장 던전의 전투 덱이다(무기 카드는 장착 무기에서 매번 추가).

## 8.2 용량

`용량 = 6 + (승급 2단계 이상 +1) + (승급 4단계 +1) + (공명 4 +1)` → 최대 9.

## 8.3 변경과 비용 (`data.rules.memoryCost`)

| 변경 | 비용 | 판정 |
|---|---|---|
| 기본(B) 카드 추가 | 1 | 기본 덱에 없는 그 캐릭터 카드 |
| 고급(A) 카드 추가 | 2 | |
| 희귀(S) 카드 추가 | 3 | 진화 카드는 원본 카드의 희귀도로 계산 |
| 공용 카드 추가 | 1 | 그 캐릭터에게 배정된 공용 카드 |
| 강화(+) | 1 | 기본 덱 카드의 강화, 또는 추가 카드에 포함 |
| 부품(일반 / 희귀) | 1 / 2 | 칸마다(회로·각인) |
| 진화 | 2 | 기본 덱 카드가 진화했거나, 추가 카드에 포함 |
| 카드 제거 | 1 | 기본 덱 카드가 덱에 없음 |

추가 카드의 비용 = 카드 비용 + (강화 1) + (진화 2) + 부품 비용 합. 예: 희귀 카드에 희귀 부품을 붙이고 강화했다면 3 + 2 + 1 = 6.

## 8.4 변경 목록 계산 (`Run.memoryChanges`)

1. 캐릭터의 기본 덱을 만든다.
2. 이번 탐사 덱에서 그 캐릭터의 카드(고유 카드, 그 캐릭터에게 배정된 공용 카드)를 모은다. 무기 카드·토큰·저주는 제외.
3. 기본 덱 카드마다 같은 ID(또는 그 카드에서 진화한 카드)를 하나씩 짝짓는다. 짝이 없으면 "제거", 짝이 진화했으면 "진화", 강화했으면 "강화", 부품마다 "부품" 변경을 만든다.
4. 짝이 지어지지 않은 나머지 카드는 각각 "추가" 변경이다.
5. 변경 목록은 결정적 순서(기본 덱 순서 → 추가 순서)를 가진다. 선택은 이 목록의 **인덱스**로 보낸다.

## 8.5 저장 규칙 (`Run.commitMemory`)

- 정상 종료(완주·귀환): 캐릭터마다 고른 변경 비용 합 ≤ 용량(`OVER_CAPACITY`).
- **패배: 파티 전체에서 변경 1개만**(`DEFEAT_KEEP_ONE`). 용량 검사도 함께 한다.
- 고르지 않은 변경은 버려지고, 덱은 기본 덱에서 고른 변경만 반영해 다시 만든다(이전 기억 덱 기준이 아니라 **기본 덱 기준**으로 차이를 계산하므로, 이전 저장 내용을 유지하려면 그 변경도 다시 선택돼 있어야 한다).
- 공용 카드 배정: 새로 얻은 공용 카드는 기본으로 편성 1번 캐릭터에게 배정되며, 저장 화면에서 바꿀 수 있다(`Run.assign`).
- 저장은 서버 트랜잭션 1회로 처리하고(§17.2) 캐릭터별 이전 덱을 `memory_deck_history`에 남긴다.

## 8.6 저장 화면 UX

- 캐릭터별 카드 영역: 용량 막대(사용/최대), 변경 목록(체크박스, 비용, 카드 미리보기), 결과 덱 미리보기.
- 기본 선택: 정상 종료면 **이전 기억 덱에 있던 변경을 먼저**, 남은 용량으로 새 변경을 목록 순서대로 체크한다(프로토타입은 목록 순서대로만 체크). 패배면 아무것도 체크하지 않는다.
- 용량 초과·패배 2개 이상이면 저장 버튼을 비활성화하고 이유를 표시한다.
- "저장하지 않기"는 확인 대화를 거친다(기억 덱은 바뀌지 않음).

## 8.7 설계 의도와 경계

- 저장은 **덱의 모양**만 남긴다. 유물·동전·체력·지도 진행은 남지 않는다.
- 용량은 레벨이 아니라 승급·공명으로만 늘어난다: 장기 목표가 되되, 무과금도 승급 4단계로 8까지 도달한다.
- 강한 카드를 무한히 쌓지 않도록 추가 비용이 희귀도에 비례한다. 카드 제거(덱 압축)에도 비용 1을 받는다.
- 패배 1개 규칙은 "도전의 대가"이며, 고난도 탐사에서도 최소한의 진전이 남게 한다.

## 8.8 현재 구현과 목표 정책

**현재 참조 구현:** 기존 Run/HTML은 v0.7의 기본 덱 재구성 정책이다. 이미 저장한 변경을 잃을 수 있으므로 가치 있는 실제 계정 데이터를 넣지 않는다. **통합 설계 목표:** 이전 기억 덱을 보존한 상태에서 탐사 성과를 선택적으로 적용한다. 제공된 `proposals/memory_v2.cjs`는 이 목표의 독립 검증 모듈이며 기본 탐사·HTML·서버 연결은 미완료다.

새 정책이 구현되면 패배의 대가는 이번 탐사의 신규 성과에만 둔다. 영구 캐릭터·무기·인연·출발 전 저장 덱은 자동 삭제하지 않는다. 패배 시 신규 변경 0~1개, 정상 귀환 시 여러 변경을 선택하되 최종 용량을 지킨다. 아무것도 고르지 않으면 출발 전 상태를 유지한다. 실패 결과를 지우기 위해 과금 부활이나 유료 복구권을 요구하지 않는다.

## 8.9 카드 개체와 네 가지 스냅샷

| 계층 | 필수 내용 | 신뢰 주체 |
| --- | --- | --- |
| 기본 덱 baseline | 캐릭터별 기본 카드 개체와 허용 소유권 | 버전 고정 콘텐츠 |
| 출발 before | 저장 스키마 버전, 안정적 key, 카드 종류, 강화·진화·영구 부품 | 서버가 출발 시 보관 |
| 종료 after | 같은 key의 변경과 이번 탐사 신규 key, 임시 토큰 표시 | 서버 참조 엔진 |
| 후보 result | 선택을 before 사본에 적용한 최종 상태 | 서버가 전부 재검증 |

`cardId`는 종류이며 `key`는 개체다. 같은 카드 두 장을 서로 다른 개체로 구분한다. 임시 전투 UID를 영구 key로 재사용하지 않는다. 진화는 같은 개체의 종류 변환이고 복제 토큰은 새 임시 개체다. 탐사 신규 카드 키는 runId와 순번으로 재현 가능하게 발급한다.

## 8.10 변경 목록과 비용

| 변경 | 선택 후 처리 | 최종 비용 원칙 |
| --- | --- | --- |
| 강화 | 지정 key의 강화만 변경 | 기본 대비 강화 비용 |
| 진화 | 허용 원본 → 허용 진화. 계보 보존 | 진화 비용 2 및 이미 보유한 다른 변화 비용 |
| 부품 교체 | 지정 슬롯의 영구 부품만 교체 | 이전 부품 비용 제거 후 새 부품 비용 |
| 새 카드 추가 | 이번 탐사에서 실제 추가된 key를 한 번만 추가 | 희귀도·강화·진화·부품 전부 포함 |
| 제거 | 정확히 지정한 개체 제거 | 기본 덱 대비 제거 비용도 계산 |
| 선택 없음 | before 그대로 | 이전 비용 그대로 |

최종 용량은 이번 선택분의 합이 아니라 **완성된 result 전체를 baseline과 비교한 비용**이다. 기존 비용 6에 신규 비용 3을 더하면 총 9이며 용량 6에서는 거절한다. 이전에 추가된 카드를 다시 신규 카드로 노출하거나 같은 key를 두 번 저장하지 않는다. 제거+추가를 패배의 ‘변경 하나’로 묶지 않는다.

## 8.11 명령과 원자성

클라이언트 요청은 `{requestId, expectedMemoryVersion, runId, selectedChangeIds}`이다. 클라이언트가 최종 덱·비용·소유권을 정하지 않는다. 서버는 계정·탐사·기억 덱 버전을 잠그고 실제 종료 상태로 변경 목록을 재산출한다.

처리 순서: 요청 식별·소유권 → 종료 상태 확인 → before/after 유효성 → 실제 diff → 패배 0~1개 제한 → before 복사본에 적용 → 소유·개체·진화·부품·용량 검사 → 이력과 새 버전을 같은 트랜잭션으로 저장 → 종료 표식·멱등 응답 저장. 오류가 나면 어떤 덱·원장·수령 상태도 바뀌지 않는다.

같은 requestId와 같은 본문은 같은 응답을 돌려준다. 같은 ID에 다른 본문은 충돌이다. 다른 기기가 먼저 저장했다면 stale version으로 거절하고 최신 내용을 표시한다. 서버에 저장 API가 아직 없는 상태에서 이 계약을 ‘시험 통과’로 표시하지 않는다.

## 8.12 저장 화면

위쪽에는 ‘출발 전에 있던 기억 — 유지’를, 아래에는 ‘이번 탐사에서 생긴 변화’를 보여준다. 패배 화면의 기본 선택은 ‘기존 덱 유지’다. 후보를 고르면 전후 카드·최종 비용·남은 용량·이번에 남기지 못하는 변화가 함께 보인다. 초과 시 비활성 이유를 표시하되 이전 덱 유지 버튼은 항상 제공한다.

정상 귀환에서는 여러 변경을 조합해 결과를 미리 보고 확정한다. 확정 이전 선택 취소에는 비용이 없다. 제출 후 통신이 끊기면 새 명령이 아니라 동일 requestId로 결과를 조회한다. 앱 종료를 패배로 판정하지 않는다.

## 8.13 용량 성장의 통합 목표

기본 6 + 승급 2단계에서 1 + 승급 4단계에서 2 = 최대 9. 공명 4의 용량 증가는 무료 승급 경로로 옮기는 목표다. 다른 공명 전투 효과의 삭제나 보상 변경은 자동으로 함께 하지 않는다. 기존 런타임 수치와 데이터 마이그레이션 전에는 해당 이동을 적용됐다고 표시하지 않는다.

## 8.15 외부 저장 패치를 채택하지 않은 이유

> **출처·상태:** v0.7.1 검토서 8쪽을 이 장에 통합. 아래 재현 수치는 해당 검토의 기록이며, 이번 재실행 결과는 §19.1 및 reports/audit_v081에서 별도로 확인한다. 목표·제안은 실행 완료가 아니다.

**이전 덱의 강화가 사라지는 현상은 재현된다. 그러나 원본 §8.5는 ‘이전 기억 덱이 아니라 기본 덱에서 재구성’한다고 명시한다.** 따라서 구현이 명세를 어긴 버그라기보다는, 영구 자산을 잃게 하는 정책과 UX 문제다. [O §8.5, p.28; R Fix 3]

외부 패치는 이전 기억 덱을 시작점으로 바꾸면서, 선택 목록은 여전히 기본 덱 대비 변경으로 계산한다. 이 둘을 섞으면 같은 변경이 두 번 적용된다.

| 독립 재현 | 외부 패치 결과 | 문제 |
|---|---|---|
| 이전 덱에 희귀 카드 2장, 비용 6 / 용량 6 | 새 희귀 카드 비용 3을 고르면 최종 비용 **9** 저장 | 선택분 3만 검사, 이전 6 누락 |
| 이전에 저장한 추가 카드가 변경 목록에 다시 나타남 | 같은 카드를 다시 선택하면 **2장** | 이전 덱에 ‘추가’를 재적용 |
| 다른 캐릭터만 선택 | 그 캐릭터 밖의 이전 덱은 보존 | 이 정상 사례만 시험하면 앞의 실패를 놓침 |

#### 이번 병합 판단
외부 Fix 3은 **병합하지 않았다**. `_added` 변수 정리는 별도 적용했지만 이를 “저장 보존 해결”이라고 부르지 않는다. 기본 HTML은 여전히 v0.7의 패배 저장 정책이며, 다음 저장 정책을 결정하기 전에는 가치 있는 테스트 덱을 잃을 수 있다. 프로토타입에는 그 주의 문구를 표시한다.

#### 제품 제안
패배의 대가는 **이번 탐사의 신규 성과 제한**에 두고, 출발 전에 확보한 덱을 자동으로 지우지 않는 방향을 추천한다. 단, 저장 상한을 지키며 변경 1개를 선택할 수 없을 때는 “기존 덱 유지”가 반드시 가능해야 한다. 이 변경에는 저장 스키마·UI·마이그레이션 설계가 필요하다.

## 8.16 마이그레이션 인수 시험과 남은 경계

> **출처·상태:** v0.7.1 검토서 10쪽을 이 장에 통합. 아래 재현 수치는 해당 검토의 기록이며, 이번 재실행 결과는 §19.1 및 reports/audit_v081에서 별도로 확인한다. 목표·제안은 실행 완료가 아니다.

| 단계 | 구현할 것 | 완료 조건 |
|---|---|---|
| M1 개체 식별 | 저장 개체 key 발급, 새 탐사에 계승 | 중복 종류·진화·복제 후에도 유일성 유지 |
| M2 변화 계산 | 출발/종료 차이, 삭제·추가·진화·강화·부품 | 기존 추가 카드가 다시 ‘신규’가 되지 않음 |
| M3 용량 검사 | 기본 덱 대비 최종 결과 비용 | 이전 비용 + 신규 비용이 상한 초과하면 거절 |
| M4 서버 적용 | 계정·덱 버전 잠금, 멱등 영수증, 이력 | 재전송·다른 기기 동시 저장에도 한 번 적용 |
| M5 화면 | 남는 것/이번에 잃는 것, 결과 덱 미리보기 | 선택 없음으로 기존 덱 유지, 비용 초과 이유 표시 |
| M6 마이그레이션 | 이전 ID-only 덱에 결정적 개체키 부여 | dry-run, 백업, 이력 대조, 재실행 동일 결과 |
| M7 C# 이식 | JS와 같은 직렬화·규칙 | 정상/실패/중복 명령 트레이스 일치 |

#### 새 회귀 시험이 막는 사례
기존 용량 6에서 비용 3 추가, 같은 종류의 두 개체 중 하나만 강화, 진화와 강화가 함께 생겼을 때 진화만 선택, 임시 부품을 영구 저장하려는 입력, 카드 종류를 임의로 다른 카드로 바꾸는 입력, 이미 저장된 추가 카드를 다시 선택하는 경로를 검사했다.

#### 정책 선택의 남은 문제
정상 완주 저장도 before 기반 누적형으로 바꿀지, 완주에서는 전체 새 덱 편집을 허용할지 결정해야 한다. 여기서 제안한 모듈은 **패배 복구의 한 변경 처리만** 담당한다. 용량이 찬 덱에서 제거+추가를 하나의 교체로 묶을지는 별도 정책이며 v0.7.1 검토에서는 허용하지 않았다.

#### 출시 전 차단
이식·마이그레이션이 준비되지 않으면 새 저장 정책을 운영 데이터에 적용하지 않는다. 숫자 1개를 바꾸는 패치가 아니라 영구 자산의 의미를 바꾸는 변경이다.
