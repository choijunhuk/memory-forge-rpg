# 기억 공방 / Memory Forge — v0.8 전체 통합 설계서

**문서 성격:** v0.7 전체 설계와 v0.7.1의 검증된 수정·보완 명세를 한 권으로 재편집한 개발 기준서. 이전 검토서를 따로 찾아서 합칠 필요가 없도록, 전투·저장·성장·과금·캐릭터·UI·운영·AI 작업 지침의 해당 장에 반영했다.

**중요한 구분:** 설계의 통합과 제품 구현 완료는 다르다. 이 패키지는 이미 수정된 JS 규칙 참조, 테스트용 HTML, 전체 콘텐츠 원본과 개발 도구를 포함한다. 저장 v2는 독립 검증 모듈까지 있으며, 기존 탐사·HTML·서버 연결은 다음 구현 작업이다. Unity 게임과 운영 서버가 완성됐다는 뜻이 아니다. 이 상태를 숨기지 않고 문서·README·HTML 안내·AI 시작 지침에 동일하게 표시한다.

### 규칙 상태를 읽는 법

**현재 참조 구현**은 이 ZIP에서 코드와 HTML로 실행할 수 있는 범위를 뜻한다. **통합 설계 목표**는 이번 문서에서 완전한 구현 계약으로 정리했지만 아직 연결되지 않은 기능이다. **비교안**은 확률·수급·나이 등 별도 결정을 기다리는 대안이며 운영 데이터를 바꾸지 않는다. 모든 수치는 밸런스·사업성 검증 전 설계 값이다.

### 구현 상태의 단일 목록

기계가 읽는 상태표는 `reports/integration_v080/status.json`이다. 문서의 기능을 보고 이미 구현됐다고 가정하지 말고, 상태표와 실제 실행 로그를 함께 본다. 이전 검토서의 시험 결과는 이전 실행 기록이며 이번 실행 결과와 혼합하지 않는다.


## 1. 게임의 핵심과 적용 범위

기억을 잃은 공방장이 동료와 시간이 멈춘 도시를 탐사한다. 세 캐릭터의 공유 덱으로 행동을 지금 쓰거나 미래에 예약하고, 캐릭터의 고유 기술을 유지한 채 회로·각인으로 개조한다. 전투 밖에서는 익숙한 캐릭터·무기·스킬·장비 성장, 모집, 인연, 주간 보스와 기간 도전을 제공한다.

기술적 수정은 기존 참조 엔진에 반영된 범위를 사용한다. 저장 보존, 무료 용량 해금, 본편 결말 분리, 초기 기록 균열 완화는 해당 장의 통합 목표와 구현 인수 조건으로 정리한다. 구현 전인 것을 현재 실행 규칙으로 표시하지 않는다. 수익 모델·확률·가격은 v0.7 값으로 유지한다.

42일 최대 반복 수급은 결정 13,920과 한정권 9장, 모집 환산 96회다. 이 중 기록 균열 최대 15회를 제외하면 기본 81회다. 68.9%는 단일 목표·가용량 96회·천장 0·확정 아님이라는 조건의 값이다. 전반·후반 배너와 신규 두 명 확보는 §12에서 분리한다.

### 5.A 통합 규칙: 첫 턴 경계와 성장 이벤트

첫 플레이어 턴에는 이전 턴이 없으므로 전투 시작 효과로 얻은 방어와 반격을 제거하지 않는다. 두 번째 턴부터는 기존 방어 정리와 보루 유지 수치를 적용한다. 전투 시작 유물·무기·공명의 지급 순서와 일반 턴 정리 순서를 별도 이벤트로 둔다.

| 재현 조건 | 첫 턴 기대값 | 다음 턴 원칙 |
| --- | --- | --- |
| 청동 톱니 8 + 장부 자물쇠 R5 8 + 하린 공명 방어 10 | 방어 26 | 보루 등 명시적 유지분 외 초기화 |
| 하린 시작 반격 2 | 반격 2 | 다음 턴 초기화 |
| 영원의 씨앗 실제 성장 + 공생 이끼 | 성장 이벤트당 방어 3 | 첫 턴 지급을 제거하지 않음 |

성장 가능 여부와 성장 계열 여부는 다르다. 유효하게 진화한 카드는 성장 계열이고 유효 성장치 3으로 읽지만 다시 성장하지 않는다. `from` 문자열만으로 인정하지 않고 원본 카드의 허용 진화 목록을 확인한다. 복제·메아리는 계보를 계승하되 무료 비용·임시 토큰 제외 규칙을 유지한다.

`applyGrowth`는 실제 성장치 증가 후 이벤트를 한 번 발생시킨다. 최대치·성장 불가·단순 조회에서는 공생 이끼가 발동하지 않는다. 필살기의 별도 성장 상한과 일반 예약 성장 상한을 혼동하지 않는다. 성장량 +2를 한 번 적용하면 이벤트 1회, +1을 두 번 적용하면 2회다. 카드별 효과 데이터가 어느 경우인지 명시해야 한다.

## 8. 기억 저장 — 보존형 v2 통합 설계

### 8.1 현재 구현과 목표 정책

**현재 참조 구현:** 기존 Run/HTML은 v0.7의 기본 덱 재구성 정책이다. 이미 저장한 변경을 잃을 수 있으므로 가치 있는 실제 계정 데이터를 넣지 않는다. **통합 설계 목표:** 이전 기억 덱을 보존한 상태에서 탐사 성과를 선택적으로 적용한다. 제공된 `proposals/memory_v2.cjs`는 이 목표의 독립 검증 모듈이며 기본 탐사·HTML·서버 연결은 미완료다.

새 정책이 구현되면 패배의 대가는 이번 탐사의 신규 성과에만 둔다. 영구 캐릭터·무기·인연·출발 전 저장 덱은 자동 삭제하지 않는다. 패배 시 신규 변경 0~1개, 정상 귀환 시 여러 변경을 선택하되 최종 용량을 지킨다. 아무것도 고르지 않으면 출발 전 상태를 유지한다. 실패 결과를 지우기 위해 과금 부활이나 유료 복구권을 요구하지 않는다.

### 8.2 카드 개체와 네 가지 스냅샷

| 계층 | 필수 내용 | 신뢰 주체 |
| --- | --- | --- |
| 기본 덱 baseline | 캐릭터별 기본 카드 개체와 허용 소유권 | 버전 고정 콘텐츠 |
| 출발 before | 저장 스키마 버전, 안정적 key, 카드 종류, 강화·진화·영구 부품 | 서버가 출발 시 보관 |
| 종료 after | 같은 key의 변경과 이번 탐사 신규 key, 임시 토큰 표시 | 서버 참조 엔진 |
| 후보 result | 선택을 before 사본에 적용한 최종 상태 | 서버가 전부 재검증 |

`cardId`는 종류이며 `key`는 개체다. 같은 카드 두 장을 서로 다른 개체로 구분한다. 임시 전투 UID를 영구 key로 재사용하지 않는다. 진화는 같은 개체의 종류 변환이고 복제 토큰은 새 임시 개체다. 탐사 신규 카드 키는 runId와 순번으로 재현 가능하게 발급한다.

### 8.3 변경 목록과 비용

| 변경 | 선택 후 처리 | 최종 비용 원칙 |
| --- | --- | --- |
| 강화 | 지정 key의 강화만 변경 | 기본 대비 강화 비용 |
| 진화 | 허용 원본 → 허용 진화. 계보 보존 | 진화 비용 2 및 이미 보유한 다른 변화 비용 |
| 부품 교체 | 지정 슬롯의 영구 부품만 교체 | 이전 부품 비용 제거 후 새 부품 비용 |
| 새 카드 추가 | 이번 탐사에서 실제 추가된 key를 한 번만 추가 | 희귀도·강화·진화·부품 전부 포함 |
| 제거 | 정확히 지정한 개체 제거 | 기본 덱 대비 제거 비용도 계산 |
| 선택 없음 | before 그대로 | 이전 비용 그대로 |

최종 용량은 이번 선택분의 합이 아니라 **완성된 result 전체를 baseline과 비교한 비용**이다. 기존 비용 6에 신규 비용 3을 더하면 총 9이며 용량 6에서는 거절한다. 이전에 추가된 카드를 다시 신규 카드로 노출하거나 같은 key를 두 번 저장하지 않는다. 제거+추가를 패배의 ‘변경 하나’로 묶지 않는다.

### 8.4 명령과 원자성

클라이언트 요청은 `{requestId, expectedMemoryVersion, runId, selectedChangeIds}`이다. 클라이언트가 최종 덱·비용·소유권을 정하지 않는다. 서버는 계정·탐사·기억 덱 버전을 잠그고 실제 종료 상태로 변경 목록을 재산출한다.

처리 순서: 요청 식별·소유권 → 종료 상태 확인 → before/after 유효성 → 실제 diff → 패배 0~1개 제한 → before 복사본에 적용 → 소유·개체·진화·부품·용량 검사 → 이력과 새 버전을 같은 트랜잭션으로 저장 → 종료 표식·멱등 응답 저장. 오류가 나면 어떤 덱·원장·수령 상태도 바뀌지 않는다.

같은 requestId와 같은 본문은 같은 응답을 돌려준다. 같은 ID에 다른 본문은 충돌이다. 다른 기기가 먼저 저장했다면 stale version으로 거절하고 최신 내용을 표시한다. 서버에 저장 API가 아직 없는 상태에서 이 계약을 ‘시험 통과’로 표시하지 않는다.

### 8.5 저장 화면

위쪽에는 ‘출발 전에 있던 기억 — 유지’를, 아래에는 ‘이번 탐사에서 생긴 변화’를 보여준다. 패배 화면의 기본 선택은 ‘기존 덱 유지’다. 후보를 고르면 전후 카드·최종 비용·남은 용량·이번에 남기지 못하는 변화가 함께 보인다. 초과 시 비활성 이유를 표시하되 이전 덱 유지 버튼은 항상 제공한다.

정상 귀환에서는 여러 변경을 조합해 결과를 미리 보고 확정한다. 확정 이전 선택 취소에는 비용이 없다. 제출 후 통신이 끊기면 새 명령이 아니라 동일 requestId로 결과를 조회한다. 앱 종료를 패배로 판정하지 않는다.

### 8.6 용량 성장의 통합 목표

기본 6 + 승급 2단계에서 1 + 승급 4단계에서 2 = 최대 9. 공명 4의 용량 증가는 무료 승급 경로로 옮기는 목표다. 다른 공명 전투 효과의 삭제나 보상 변경은 자동으로 함께 하지 않는다. 기존 런타임 수치와 데이터 마이그레이션 전에는 해당 이동을 적용됐다고 표시하지 않는다.

## 10.1 무기 체계

- 캐릭터마다 무기 종류(원거리·근접·장치·의식)가 정해져 있고 **같은 종류만 장착**한다. 한 무기는 한 캐릭터만 장착한다(서버 고유 제약).
- 장착 무기는 ① 전투력(§11.1 W) ② 패시브(정련 R1~R5) ③ **무기 카드 1장**(장착자 속성, 장착자의 카드로 취급: 게이지·잔향)을 준다.
- 등급: 전용 SSR 6(한정 2 + 상시 4, 해당 캐릭터에게 맞춘 패시브), 범용 SSR 4, SR 8, 기본 R 4(종류마다 1개, 제작·기본 지급, 패시브 대신 정련 시 피해·방어 +0~12%).
- 정련: SSR·SR은 같은 무기 중복 획득으로 R1→R5(5개째 이후 초과분은 기억 결정체). 기본 R 무기는 **제련핵**(보스 토큰 교환, §12.5)으로 정련한다.
- 무기 레벨·승급은 §11.

## 11.1 전투 스탯 모델

카드 수치는 탐사 안에서만 바뀐다. 계정 성장은 **전투력**과 **체력**, 스킬 배율, 장신구 가산으로만 전투에 들어간다.

```text
캐릭터 전투력 C(Lv)  = 20 + floor(14 × Lv / 60)              ; Lv.1 20 · Lv.30 27 · Lv.60 34
무기 전투력   W(wLv) = SSR 2 + floor(6×wLv/60) · SR 1 + floor(5×wLv/60) · R 1 + floor(3×wLv/60)
전투력 P = C + W,  power4 = 4P                                 ; 피해·방어 × power4 / 160
캐릭터 체력 = 60 + Lv (+ 갑주: (2 + n) + floor((60 + Lv) × (300 + 60n) / 10000))
파티 체력 = 3명 합
장신구 +n  = 그 캐릭터 카드(무기 카드 포함)·필살기의 피해·방어 가산 +(250 + 50n) bps
방어·회복   × 캐릭터 체력 / 81  ; 공격은 전투력, 방어·회복·체력 대가는 체력에 비례(§5.12 고정 수치 규칙)
스킬 배율   = 1 + 0.04 × (레벨 − 1)  ; 카드 스킬(고유 카드), 필살기 스킬 각각. 공명 3·5가 +2씩(최대 12)
```

**스테이지 배율**(이 레벨에 맞는 파티가 기준 전투와 같은 체감이 되게 하는 적 배율):

```text
P_ref(L) = C(L) + W_SR(L)
적 체력 % = round(100 × P_ref(L) / 40)
적 피해 % = round(100 × (60 + L) / 81)
```

- 기준 전투(프로토타입 시험 모드)는 전투력 40, 체력 81, 배율 100%/100%다. 실제 콘텐츠는 레벨에 맞는 배율을 쓰므로, **같은 레벨이면 기준 전투와 같은 난도**, 레벨이 높으면 쉬워지고 낮으면 어려워진다.
- 장비·스킬·공명·SSR 무기는 기준선에 포함하지 않은 **순수 이득**이다(그래서 공명 0·SR 무기로도 깰 수 있게 맞춘다).

## 11.2 레벨·경험치

- 캐릭터 레벨 L→L+1 경험치 = 40 × (4 + L + floor(L²/10)). Lv.1→60 합계 **360,000**. 무기는 절반(180,000). 크레딧 = 경험치 × 0.5.
- 경험치 아이템: 기록 잉크 소 1,000 · 중 5,000 · 대 20,000(무기는 태엽 기름 같은 단위). 넘치는 경험치는 다음 레벨로 이월하되 레벨 상한에서 멈추고, 상한에서 남는 아이템은 소비하지 않는다(서버가 최소 조합 자동 선택).
- 레벨 상한: 승급 0단계 20, 1단계 30, 2단계 40, 3단계 50, 4단계 60. 승급은 레벨이 상한에 도달했을 때만 가능하다. **Lv.60이 출시 상한**(v0.6의 Lv.80 표기는 폐기).

## 11.5 성장 던전

- 6종(잉크·크레딧·태엽·인장·교본·연마). 해금은 계정 레벨(§11.1 표). 각 던전은 스테이지 레벨 10·20·30·40·50·60 단계가 있고, 보상은 단계에 따라 25%·40%·55%·70%·85%·100%(표의 값은 60단계 기준).
- 전투: 저장 덱으로 단일 전투(1~3웨이브). *웨이브 진행은 명세만 있고 엔진에는 아직 없다(P2-3).* 별 3개 = 승리 + 4턴 이내 + 체력 50% 이상. 별 3개 클리어 후 **소탕**(전투 없이 같은 보상, 같은 집중).

## 11.6 주간 보스

## 11.7 기록 균열 (2주 순환 고난도)

- 해금 계정 20. 6층, 층마다 **3연전**: 1전·3전은 1파티, 2전은 2파티가 싸운다(서로 다른 6명 → 육성 폭을 요구). 파티별 체력은 그 층 안에서 이어지고(1파티는 1전에서 남은 체력으로 3전), 덱·예약·게이지는 전투마다 초기화한다. 보유 캐릭터가 6명 미만이면 2파티에 1파티 인원 재출전을 허용하되 그 층 별 최대 2개.

- **무작위는 서버 CSPRNG**로 뽑는다. 전투용 시드 RNG를 모집에 쓰지 않는다. 천장 상태 기계는 JS·C#·서버가 같고, 같은 난수열을 넣으면 같은 결과가 나오는지 교차 벡터로 검사한다(`engine/tests/vectors`).
- 결과·차감·중복 보상·천장 상태·원장·영수증을 **한 트랜잭션**에서 저장한 뒤 연출을 시작한다(§17.2). 연출을 건너뛰거나 앱이 꺼져도 결과는 보존된다.

v0.7은 디렉터 요청(반천장·중복 성능·무기 모집)을 반영해 **픽업 확보가 더 어려워졌다**. 출시 전 사업 검토에서 다음 조정 손잡이 중 무엇을 쓸지 결정한다(§22): ① 시즌 수급을 한정 110~120회 수준으로 상향 ② 픽업 확률 55% ③ 픽뚫 누적 보정(예: 직전 픽업 성공 뒤 50:50에서 진 횟수만큼 다음 50:50 확률 +10%p, 확정 규칙은 그대로) ④ 첫 한정 배너 픽업 확률 상향(신규 이용자 한정). 어떤 손잡이든 `content/gacha.mjs` 수정 → `tools/verify_economy.py`로 표를 다시 만든다. 현재 값은 **가설**이며 시뮬레이터로 체감을 먼저 확인한다.

- 결제 검증은 서버에서 Play Developer API로 하고, 구매 토큰 다이제스트로 중복 지급을 막는다. 운영 서버는 시작 시와 요청마다 모의(mock) 검증을 거부한다.

| 기억 저장 | §8.6 | 용량 초과·패배 2개 이상 저장 불가 |
| 모집 | 배너 탭, 키아트, 천장 막대(소프트 시작 표시), "다음 SSR 픽업 확정" 상태, 1회/10회 버튼(모집권·결정 표시), 확률표 링크, 결과 화면(희귀도·NEW·공명/정련·픽뚫), 기록 | 결정 부족 시 상점 이동 제안, 연출 건너뛰기 |

## 14.5 온보딩 순서

1. 프롤로그 1전투: 카드 지금 사용만(행동력·손패 설명).
2. 2전투: 다음 턴 예약 + 적 의도 2개 보기.
3. 3전투: 약점·균열 + 필살기.
4. 보스: 다다음 턴 예약 + 균열 타이밍 맞추기(실패해도 승리 가능한 수치).
5. 첫 기억 저장(용량 6 중 3 쓰기 안내), 니아·하린·리엔 지급.
6. 초심자 모집 10회(모집권 지급) → 2장 해금 시 공방(변주)·계약 소개, 3장 전 주간 보스 소개.

각 단계는 "설명 1문장 + 직접 해 보기"로 구성하고, 설명 텍스트는 3줄을 넘지 않는다. 건너뛰기를 허용하되 기억 저장 안내는 건너뛸 수 없다.

## 14.6 접근성·현지화

- 텍스트는 모두 키 기반(`ui.battle.endTurn`), 카드 텍스트는 효과 데이터에서 언어별 생성기로 만든다(직접 번역 문자열 금지).
- 한국어 기준 길이 + 영어 140%·일본어 100% 여유로 레이아웃을 검사한다.
- 색약 모드: 속성 아이콘 모양 구분(번개·불꽃·눈송이·고리) 유지, 붉은/초록 대비 대신 밝기 대비.

## 15.1 아트 디렉션

- 키워드: **밤의 공방, 황동 계기, 멈춘 시계, 번지는 잉크, 기억의 빛(청록)**. 배경은 어둡고 차분하게, 캐릭터와 카드 테두리(속성색)가 가장 밝게.

- 적: 잉크·종이·황동 부품이 뭉친 형체. 사람 얼굴을 직접 그리지 않는다(공포 수위 15세 이내).

## 15.4 이미지 생성 운영 (기본: Codex의 이미지 생성, 선택: 로컬 모델)

1. **참조 고정**: 캐릭터마다 [SHEET] 프롬프트로 디자인 시트를 먼저 확정한다. 이후 모든 생성은 확정 시트를 참조 이미지로 넣고, 같은 핵심 키워드(외형·의상·무기·팔레트)를 그대로 반복한다.
2. **생성 → 선별 → 수정 → 사람 리터치**: 한 장면당 4~8장 생성 → 기준 체크리스트(§15.5)로 선별 → 부분 수정(인페인팅) → 아티스트가 손·무기·의상 디테일·선 정리. 최종 자산은 사람이 손본 레이어 PSD를 원본으로 보관한다.
3. **기록**: 자산마다 프롬프트·참조 이미지·도구/모델 이름·날짜·수정자를 `art/provenance.csv`에 남긴다(저작권·재현성·스토어 문의 대응).
4. **정책**: 생성 도구의 이용 정책을 따른다. 15세 기준을 넘는 노출 생성은 시도하지 않는다. 10대 캐릭터에는 아래 [10대 규칙] 블록을 반드시 붙이고, 성인 팬서비스 키워드를 섞지 않는다. 로컬 모델을 쓰더라도 같은 규칙과 검수를 적용한다.
5. **스타일 일관성**: 공통 STYLE 문장을 바꾸지 않는다. 바꿀 때는 아트 디렉터 승인 후 모든 캐릭터 시트를 재확정한다.

### 15.5 최종 아트·표현 검수

캐릭터 식별, 의상 구조, 무기·소품, 얼굴과 표정, 동작 방향, 작은 화면에서의 가독성, 리깅 가능성, 스킨 상품 범위를 검수한다. 자산의 목적이 설정 시트인지 키아트인지 카드 그림인지에 맞게 포즈를 평가한다. 공통 표현 기준은 §9.1을 사용하며 모든 캐릭터를 중립 자세·보수적인 의상으로 획일화하지 않는다.

수정이 필요하면 구체적인 자산·프레임·대사·문제 이유와 대안을 남긴다. 수정 전 자료가 없으면 ‘복원’이라고 부르지 않는다. 성인 캐릭터의 매력 표현과 연령에 맞는 청소년 캐릭터의 개성·교감을 구분하되 일상적인 의상과 활발한 움직임을 일괄 삭제하지 않는다.

# <a id="ch16"></a>16. 기술 설계

## 16.1 구성

```wire
content/*.mjs ──(node content/build.mjs)──▶ data/game_data.json  ◀── 단일 데이터 원본(규칙 버전 + 해시)
      │                                          │
      │                     ┌────────────────────┼─────────────────────────┐
      ▼                     ▼                    ▼                         ▼
tools/gen_docs.mjs   engine/rules-core.js   core/MemoryForge.Core(C#)   server(ASP.NET Core)
(문서 표 생성)        JS 규칙 참조·프로토타입    netstandard2.1 · C# 8         .NET LTS + PostgreSQL 16
                     ·봇·벡터 생성             Unity 클라이언트 + 서버 공유    권위 판정·원장·모집
                            │                    │  ▲                          │
                            └── 교차 벡터 ───────┘  └──── 같은 코어 DLL ───────┘
                                                       Unity 6 클라이언트(연출·입력·캐시)
```

- **권위**: 전투·탐사·모집·재화는 서버가 판정한다. 클라이언트는 같은 C# 코어로 **미리보기**(버튼의 예상 피해)와 연출만 계산한다. 서버 응답의 공개 상태가 항상 우선한다.
- **데이터 한 벌**: 클라이언트·서버·문서·프로토타입이 같은 `game_data.json`을 쓴다. 클라이언트는 시작 시 `/content/version`으로 규칙 버전·해시를 확인하고 CDN에서 해시 주소의 데이터를 받는다. 버전이 다른 명령은 서버가 `409 CONTENT_OUTDATED`로 거절한다.

## 16.2 규칙 코어 이식 (JS → C#)

| 단계 | 내용 | 확인 |
|---|---|---|
| 완료 | `Rng`, `Gacha`(상태 기계), `Stats`, `ReservationBook` | `CoreChecks` 202/202 |
| P1 | `Battle` 전체(효과 op 39종, 적 행동 12종, 유물 32·부품 16·무기 패시브 17종), `Run`, 기억 저장 | 아래 교차 시험 |
| P2-3 | JS·C# 동시: 전투 수정자(기록 균열 규칙 6종), 연전 진행기(층 3연전·2파티·파티별 체력 이월), 웨이브 진행(성장 던전 1~3웨이브) | 단위 시험 + 트레이스 |

교차 시험 방식: JS가 `(시드, 데이터 해시, 명령 목록)` 시나리오 1,000개를 무작위 봇으로 만들고 각 명령 뒤의 상태 해시(정렬된 JSON의 SHA-256)를 저장한다(`tools/gen_traces.mjs`, P1 작성). C#은 같은 명령을 재생해 모든 해시가 같아야 통과. 규칙: 부동소수점 금지(정수·BigInteger), 모든 반올림은 명세 그대로(내림·JS `Math.round` 동치), 컬렉션 순회 순서 고정(등장 순서).

## 16.3 결정론과 숨겨진 정보

- 전투 RNG 상태와 뽑을 더미 순서는 서버 비공개 상태(`run.private_state`, `battle.private_state`)에만 있다. 공개 상태는 `publicView`: 뽑을 더미 장수, 손패, 버린·소멸 더미, 예약, 적의 현재·다음 의도.
- 같은 초기 상태 + 같은 명령열 = 같은 결과(재현). 고객 문의·치트 의심 시 서버에서 재생해 검증한다.
- 모집 RNG는 CSPRNG(`RandomNumberGenerator`)로 매 회 0~9999 정수(roll_bps)와 풀 선택 인덱스를 뽑아 기록한다. 시드 RNG를 모집에 쓰지 않는다.

## 17.2 핵심 트랜잭션

모든 쓰기 요청은 같은 골격을 따른다.

```text
BEGIN
  1. command_receipt 조회: 같은 request_id가 있으면 → 요청 해시 같음: 저장된 응답 반환 / 다름: 409 IDEMPOTENCY_CONFLICT
  2. 잠금(항상 같은 순서): account_progress → wallet(재화 이름순) → inventory(아이템 이름순) → 대상 행(gacha_pity / character_owned / run …) FOR UPDATE
  3. 규칙 실행(C# 코어). 실패 → ROLLBACK + 422 {code}
  4. 상태 행 갱신(version + 1), ledger 행 추가, 결과 행 추가
  5. command_receipt 저장(응답 본문 포함)
COMMIT → 응답
```

| 트랜잭션 | 단계 4의 내용 |
|---|---|
| 모집 1/10회 | 모집권·결정 차감(원장), 10회 결과 `gacha_pull` 10행(roll_bps 포함), 보유 캐릭터·무기 copies 증가 또는 신규 행, 기억 결정체·잔광 지급(원장), `gacha_pity` 갱신 |
| 레벨업 | 아이템 차감(최소 조합), 크레딧 차감, 레벨·경험치 갱신(상한에서 정지) |
| 승급·스킬·장비 | 재료·크레딧 차감, 단계 +1(계정 레벨 조건 검사) |
| 탐사 명령 | `run.private_state` 갱신, state_version + 1, 이벤트 반환. 탐사 안의 동전 등은 원장 밖(탐사 상태) |
| 기억 저장 | `Run.commitMemory` 실행 → 캐릭터별 `memory_deck` 교체 + 이전 판 `memory_deck_history`, run.status = saved |
| 주간 보스 보상 | 승리한 battle 확인 → `weekly_claim_counter` +1(최대 3, 초과 시 422 WEEKLY_LIMIT) → 승급 핵·크레딧·토큰 지급 |
| 구매 | Play Developer API 검증 → `purchase` 삽입(토큰 다이제스트 유일) → 지급(원장) → 커밋 후 acknowledge/consume. 지급 전 실패는 다음 로그인 때 재시도 |
| 우편 수령 | 만료 확인 → 첨부 지급(원장) → claimed_at |

### 19.1 검증 상태

### 19.3 밸런스 측정 설계

같은 파티·무기·공명·기억 덱·적·시드를 모든 플레이 정책에 사용한다. 무작위·탐욕·계획 봇의 차이를 파티 차이로 설명하지 않는다. 요청한 반복 수와 실제 조우 수×정책 수×반복 수를 모두 보고한다. 승리뿐 아니라 패배·시간 초과를 포함해 턴 p50/p90, 체력 손실, 예약 빈도를 저장한다.

구역 1·2만 도는 러너로 구역 3~5를 검증했다고 하지 않는다. 새로운 적 행동·조우·후반 대본은 별도로 실행 경로가 확인되어야 한다. 봇의 승률로 사람이 반드시 더 잘한다고 가정하지 않는다. P0에서 사람 플레이와 이해도·오조작을 측정한다.

### 19.4 아직 제품 검증이 아닌 것

브라우저 자동 진행은 Unity Play Mode·Android 실기기를 대신하지 않는다. C#의 RNG·모집·스탯·예약 장부 검사 통과는 Battle/Run 전체 이식 통과가 아니다. DB 스키마 적용은 서버 애플리케이션·결제 검증의 완성이 아니다. 실결제·운영 배포·부하 시험을 별도로 기록한다.

## 19.2 엔진 단위 시험이 보장하는 것

RNG 결정론·경계, 교차 벡터 일치, 메아리·복제 토큰 비용 0 유지, 레벨 대응 배율(방어·회복 = 체력, 반격 = 전투력, 반사 = 스테이지 %), 상점 유물 2개·사건 희귀도(RNG·모집·스탯), 데이터 인덱스, 전투 시작 상태, 기준 전투 피해, 예약 칸(2/1, SLOT_FULL, 다음 턴 해결), 실패 명령의 원자성·사전 검사의 순수성, 멱등·충돌·오래된 버전, 균열(게이지·행동 취소·+25%·행동력 +1), 손패 상한·카드 보존, 계약(선불·부채 상한), 성장 스탯·스테이지 배율·경험치 합 360,000, 장신구 가산, 지도 보장(300시드), 기억 저장(용량·패배 1개·재구성), 용량 성장, 모집(하드 80·픽뚫 확정, SR 10회, 무기 70·75%, 평균 = 정확값 ±3% 몬테카를로, 초심자 50회, 횟수 1/10, 선택권 300, 공명·정련 상한).

# <a id="ch20"></a>20. 단계별 제작 계획 (AI 에이전트용)

## 20. Claude·Codex·Unity MCP 제작 실행 계획

### 20.1 읽기 순서와 실제 기준

두 에이전트 모두 `AGENTS.md` → `docs/CURRENT.md` → `docs/design_v0.8.md` → `reports/integration_v080/status.json`을 읽는다. 숫자·카드 정의는 현재 `data/game_data.json`, 실행 참조는 `engine/rules-core.js`다. `data/design_policy_v0.8.json`은 목표 정책과 활성 상태를 분리한 계약이다. 이 파일을 읽었다는 이유만으로 게임 규칙이 바뀌지는 않는다.

### 20.2 역할과 편집권

| 영역 | 작성 | 검토 | 병렬 작업 조건 |
| --- | --- | --- | --- |
| 전투·저장·서버 | Codex | Claude + 회귀 시험 | API/상태 계약을 먼저 고정 |
| UI·콘텐츠·문서 | Claude | Codex + 화면 시험 | 데이터 필드 이름과 오류 코드 공유 |
| 경제·과금 | 한 에이전트가 제안 | 다른 에이전트 독립 계산 + 사람 승인 | 같은 수급표를 서로 다른 방식으로 검산 |
| 아트·서사 | Claude 또는 아트 담당 | 사람 + 캐릭터 일관성 검수 | 나이·직책·의상·대사 원본 변경 이력 |
| Unity MCP | 편집권을 가진 한 작업자 | 결과 스크린샷·씬 diff | 같은 씬·프리팹 동시 수정 금지 |

각 작업은 별도 브랜치와 worktree를 쓴다. 씬 편집권 파일에는 프로젝트 경로, 작업자, 작업 범위, 시작 시각, 만료/반납을 기록한다. 잠금은 충돌을 줄이는 작업 규칙이지 운영 권한이나 보안 경계를 대신하지 않는다. MCP 서버와 Unity 패키지 버전은 검증한 조합으로 고정하고 연결·Play Mode·파일 생성 로그를 남긴다. 프로젝트 밖 파일·실사용자 데이터·운영 비밀키를 읽도록 허용하지 않는다.

### 20.3 P0: 저장 정책을 실제 흐름으로 연결

Codex는 안정적 카드 key·출발 스냅샷·종료 diff·최종 비용·이관 어댑터를 구현한다. Claude는 ‘기존 기억 유지’ 기본 선택, 신규 변화 0~1개, 용량 초과 이유, 전후 미리보기를 연결한다. 두 작업자는 같은 요청 DTO와 오류 코드를 쓴다.

통과 조건은 독립 모듈 시험만이 아니다. 기존 저장 덱으로 탐사 시작 → 패배 → 선택 없이 이전 덱 유지, 신규 변화 하나 저장, 최종 용량 초과 거절을 실제 HTML 클릭으로 확인한다. 재로딩·동일 요청 재전송·두 같은 종류 카드·진화와 강화의 분리 선택을 검사한다. 이 조건을 통과한 뒤에만 HTML의 저장 v2 미연결 경고를 제거한다.

### 20.4 P1: C#·서버

C# Battle·Run·저장 로직은 검증된 JS 동작을 netstandard2.1/C# 8의 제한 안에서 이식한다. 기존 RNG·가챠·스탯·예약 장부의 검사 수를 전체 전투 완성으로 해석하지 않는다. 정수/BigInteger 반올림·컬렉션 순회 순서·직렬화 필드 순서를 정의하고 같은 시드·명령에 대해 명령별 상태 해시를 비교한다.

서버는 계정·콘텐츠 버전·모집·성장·탐사·전투·기억 저장 API를 구현한다. 계정 잠금 → 요청 해시/멱등 확인 → 규칙 → 상태·원장·이력 → 영수증 → 커밋의 일관된 계약을 지킨다. DB 스키마의 기존 제약 검사는 서버의 거래 검증과 별도다.

### 20.5 P2: 콘텐츠와 화면

후반 여섯 행동의 효과·의도·실패 경계를 먼저 구현한 뒤 3~5구역 적을 연결한다. 전투 준비, 대본 준비, 아트·음성 준비를 각기 다른 플래그로 둔다. 본편 인장 6개·인연 20조각·기록 균열 팀 완화·무료 용량 변경을 데이터와 화면에 동시에 반영한다.

Unity에서는 로비 → 편성 → 지도 → 전투 → 보상 → 저장을 실제로 한 판 이어간다. 큰 글자·최대 손패·예약·최대 적·앱 복귀·통신 끊김을 검사한다. 실기기의 조작성과 성능은 브라우저 픽셀 검사와 분리한다.

### 20.6 P3: 상용 운영 전환

월정액·패스·상점·영수증 검증·환불 상태·공지·고객지원·운영 도구를 연결한다. local/dev/staging/production의 계정·DB·키·재화를 분리한다. 테스트 결제가 production 지급으로 넘어가지 않게 발급자·상품·환경을 확인한다. 원격 production 배포·실결제 검증은 별도 사람 승인 후 수행한다.

## 22. 남은 결정과 다음 구현 순서

첫 구현은 저장 v2를 독립 모듈 상태에서 실제 Run·HTML로 연결하는 작업이다. 그 뒤 무료 용량 성장·본편 결말 경로·기록 균열의 팀 요구를 원자적으로 연결한다. 확률·수급 증가는 비교안으로만 유지하며 사람이 선택하기 전에는 코드에 반영하지 않는다.

| 우선순위 | 작업 | 완료 조건 |
| --- | --- | --- |
| P0-A | 저장 v2 어댑터·안정적 개체키·기본 HTML 연결 | 패배 저장 UI 실제 3경로, 기존 보존·용량·복제 방지 시험 |
| P0-B | 후반 행동·소규모 조우 | 여섯 op의 예고/효과/정리/실패 경계, 실제 러너 적용 |
| P0-C | 공통 무료 용량·결말·초기 1팀 | 데이터·UI·세이브 이관 및 기존 계정 영향 검사 |
| P1 | C# Battle·Run 이식, 서버 골격 | JS 명령별 상태 해시·멱등/동시성 계약 시험 |

가격과 확률, 성인 연령 재구성의 실제 메타데이터 이관, 성우 범위, 아트 외주 예산, 신규 두 명/42일 제작 주기의 유지 여부는 별도 결정 항목이다. P0 작업자가 사업 결정을 대신하지 않는다.

### 11.B 주간 보스·기록 균열·일일 활동

주간 보스는 전 보스 공유 보상 3회, 실패 미차감, 연습 무제한이다. 승급 핵 수급이 주된 역할이며 별도 스토리 하드 메뉴로 동일 재료를 이중 강제하지 않는다. 자유 탐사의 어려움은 자율 난도 선택으로 구분한다.

기록 균열의 통합 목표는 1~3층 한 팀, 4~6층 두 팀이다. 첫 세 층의 완전 보상은 520/800=65%이며 1성분만 얻으면 312/800=39%다. 단계·별 조건을 생략하고 초보자가 대부분을 받는다고 설명하지 않는다. 실제 연전 진행기 구현 여부는 상태표를 따른다.

일일 활동은 선택형 100점이다. 전원 레벨 상한인 계정에서도 가능한 임무 조합을 제공한다. 레벨업·강화를 매일 필수로 요구하지 않고 콘텐츠 완료·집중 정산·교류 등 대체 행동으로 달성할 수 있게 한다. 보상 없는 재화 소모를 유도하지 않는다.



### 12.A 수급 확률과 배너 기간의 해석

현재 68.8886%는 천장 0·확정 아님에서 시작해 특정 픽업이 열려 있는 동안 96회를 사용할 수 있을 때 그 픽업을 적어도 한 번 얻는 확률이다. 시즌에는 21일씩 서로 다른 신규 픽업 두 명이 있다. 전반 배너가 끝난 뒤 받은 재화를 전반 캐릭터에 쓸 수 없으므로 42일 총량을 모든 배너의 가용량으로 취급하지 않는다.

| 질문 | 사용할 계산 |
| --- | --- |
| 한 목표에 96회 사용 | 68.8886%, 기존 곡선 그대로 |
| 시즌 두 신규 모두 확보 | 각 배너 지급 시점과 뽑기 중단·이월 정책을 포함한 상태 분포 |
| 첫 21일 목표 확보 | D21까지 수령·사용 가능한 재화만 |
| 신규 계정 체감 | 해금일·초심자·스토리 일회성·고난도 참여율을 별도 모델 |
| 캐릭터와 무기 함께 확보 | 분리된 천장과 동일 지갑의 지출 배분 |

기존 원장의 D21 결정 6,560에 한정권 5장이 도착한다고 가정하면 전반 46회, 시즌 96회다. 저축·이전 천장·확정·무기 지출 없이 A를 얻으면 멈추고 B로 이월하는 **분석 시나리오**에서는 A 18.07%, B 59.13%, 모두 8.31%, 둘 중 하나 이상 68.89%다. 한정권 5장의 시점은 실제 라이브 일정 확정 전의 가정이며 이 수치를 모든 계정의 확보율로 광고하지 않는다.

| 한 목표 가용량 | 현행 픽업 50% | 비교안 55% |
| --- | --- | --- |
| 81회 | 61.75% | 65.57% |

위 55%·110~120회는 비교안이다. 이 통합 과정에서 확률·가격·무료 지급량은 변경하지 않는다. ‘마지막 픽업 이후 두 번 픽뚫이면 보정’은 현재 다음 SSR 확정·픽업 시 초기화 규칙에서 두 번에 도달할 수 없어 채택하지 않는다. 새로운 연패 보호를 만들 때는 비확정 판정만 세는 별도 상태 기계를 명세해야 한다.

### 12.C 사업성 검증과 변경 승인

월정액·패스·스킨의 가격표는 판매 검증 전 가안이다. 한 시즌 신규 두 명은 카드 외에 원화·리그·키아트·인연·음성·모든 기존 조합 QA를 필요로 한다. 무료 접근성을 낮추면 매출이 자동으로 오른다는 가정을 두지 않는다. 구매 전환, 잔존, 환불, 제작비는 실제 테스트와 견적으로 검증한다.

수치 변경은 제안 → 독립 계산 → 클라이언트·서버·확률표 일치 시험 → 사람 승인 → 버전 변경의 순서다. AI는 확인되지 않은 디렉터 요청이나 기존 댓글을 근거로 가격·천장·재화 지급량을 바꾸지 않는다.



### 14.A 정보 밀도와 안전한 입력

테스트 최악 조건은 손패 10장·예약 5슬롯·적 5명·유리 성장·라비엔 부채·다수 상태·큰 글자 모드다. 작은 화면에서는 예약 슬롯을 줄이지 않고 현재 만기 그룹을 펼치며 다른 그룹은 사용량과 중요 경고를 요약한다. 행동력 차입은 HP 근처의 `다음 AP 4→2`, 성장치는 해당 카드의 핍으로 보여준다.

카드 선택 → 방식 선택 → 대상/슬롯 미리보기 → 확정은 서로 다른 상태다. 첫 탭이나 드래그 손 떼기만으로 의도하지 않은 소비가 일어나지 않는다. 확정 전 취소는 비용 0. 미리보기는 상태 사본에서 계산하고 숨겨진 드로우·난수를 노출하거나 소모하지 않는다. 요청 후 네트워크가 끊기면 동일 requestId로 조회하며 이중 사용을 막는다.

브라우저 픽셀 검사는 모바일 실기기 터치 검증을 대신하지 않는다. 48dp, 글자 배율, 안전 영역, 양손·한손 사용, 손가락 가림은 Unity 실기기 단계에서 별도 통과해야 한다. 미연결 기능의 버튼은 ‘완료’처럼 보이게 하지 않고 개발 상태를 명시한다.
