1 · 결론

한눈에 보는 결론

  • 강점

    규칙 코어는 믿을 만하다. JS 참조 엔진과 C# 공유 Core가 1,000개 탐사, 273,504개 명령을 끝까지 같은 상태로 재생한다. 오늘 별도 복제본에서 다시 돌려도 JS 333건과 C# 16개 결과 묶음이 모두 통과했다.

  • 높음

    사람 플레이 시험 기록이 없다. 원래 계획의 첫 칸인 P0-1(10판, 예약·균열 이해 80%, 재플레이 의향 70%)이 비어 있다. 설계서가 첫 번째 위험으로 꼽은 ‘예약·균열 규칙이 초보자에게 어렵다’의 대응책 셋(온보딩, 버튼 미리보기, 이해도 측정) 가운데 미리보기만 만들어졌고, 그사이 이식과 화면 연출이 쌓이고 있다.

  • 높음

    후반 콘텐츠는 저절로 풀리지 않는 잠금에 걸려 있다. 목표 미달 32개·21개는 단순 봇으로 잰 값이다. 원래 계획은 수치 조정을 AI에게 맡겼지만 이후 규칙은 원문 수치를 보존하라고 한다. 어느 쪽을 따를지 사용자가 정하기 전에는 구역 3~5와 4~6장을 열 수 없다.

  • 높음

    서버가 멈춰 있다. C# 이식이 끝난 뒤 작업은 ‘Unity에서 결과가 보이게 하라’는 사용자 우선순위에 따라 Unity 원정 화면으로 갔고, 서버(P1-2)는 작업 지시가 하나도 없다. 원정 화면의 기억은 앱을 닫으면 사라지고, 수직 슬라이스 완료 조건인 ‘dev 서버와 연결해 한 판 완주’에는 닿을 수 없다. C# Core에도 저장 상태 복원과 원자적 탐사 명령이 없어 서버보다 먼저 손볼 곳이 있다.

  • 중간

    속도에 비해 통합과 문서가 뒤처진다. 약 38시간 동안 32개 개발 커밋이 초안 PR 두 개에 쌓였고 main에는 최초 커밋 하나뿐이다. 현재 상태 문서는 띄어쓰기가 사라질 만큼 압축된 누적 로그가 됐고, 사용자 결정 항목은 여러 문서에 흩어져 있다.

제품과 방향

사람 플레이 시험 기록이 없다

높음

계획 §20.8의 첫 단계 P0-1(사람 플레이 10판 이상, 예약·균열 이해 80%, ‘다시 하고 싶다’ 70%)을 실행한 기록이 없다. 사용자가 macOS 빌드에서 지도 칸을 눌러 전투로 넘어가는 것을 확인한 기록은 있지만, 그것은 입력 확인이지 플레이 시험이 아니다. 밸런스는 random·greedy·planner 세 봇으로만 쟀고, 감사 보고서 스스로 이 봇들이 최적 플레이어가 아니라고 적는다.

설계서 §22.2가 꼽은 첫 번째 위험은 ‘예약·균열 규칙이 초보자에게 어렵다’이고, 대응책은 온보딩 4단계, 버튼 미리보기, P0-1 이해도 측정 셋이다. 미리보기는 만들었지만 온보딩과 이해도 측정은 아직 없다.

HTML 시제품은 지금도 탐사 편성부터 기억 저장까지 한 판을 돌릴 수 있다(설계서 §1.5). 시험 비용은 낮고, 결과에 따라 이식·화면 작업의 방향이 바뀔 수 있다.

서버는 스키마, API 계약, SQL 제약 시험만 있고 애플리케이션 코드가 없다. 설계서 17장 다섯 절 가운데 트랜잭션(§17.2)과 저장 v2 접합(§17.5)은 미구현이고, 나머지 셋은 스키마·계약 수준의 부분 구현이다. 서버 작업 지시는 0개다. Unity를 먼저 보이게 한 것은 사용자 요청이었지만, 서버를 언제 다시 잡을지는 정해지지 않았다. Unity 원정 화면은 지도→전투→보상→기억 선택→다음 출발까지 동작하지만, 기억은 앱을 닫으면 사라지고 중도 복원도 없다.

수직 슬라이스(P3-1)의 완료 조건은 ‘dev 서버와 연결해 짧은 탐사 1판 완주와 기억 저장’이다. 지금 구조로는 이 조건에 닿을 수 없어서, Unity 쪽 작업을 아무리 더해도 이 단계는 끝나지 않는다.

기술과 코드

JS 기준과 C# 이식을 맞추는 체계가 단단하다

강점

JS 엔진을 기준으로 삼고, 생성기 14개가 그 동작을 시험 자료로 고정하며, C# Core가 그 자료를 다시 실행해 정규화한 상태의 SHA-256을 비교한다. 오늘 복제본 실행에서 데이터 파일과 RNG·모집 벡터를 다시 만들어도 커밋본과 바이트 단위로 같았고, 큰 시험 자료는 시험 안에서 다시 계산해 커밋본과 대조했다. 알 수 없는 콘텐츠를 만나면 Core가 조용히 넘어가지 않고 오류로 멈춘다.

C# Core에 서버가 쓸 기능이 아직 없다

높음

서버는 요청마다 저장된 상태를 불러와 명령을 적용해야 하는데, Core에는 저장 상태를 되살리는 입구가 없다(Battle.cs:22 ‘restoration is not exposed’). 같은 요청의 재전송을 판별하는 전투 영수증은 저장 상태 밖의 메모리에만 있어서(rules-core.js:247), 복원 뒤 재시도는 저장된 응답 대신 버전 충돌을 받는다. 탐사 명령은 실패해도 일부 변경이 남을 수 있는데, API 계약은 ‘원자적, 실패 시 변화 없음’을 약속한다(server/openapi.yaml:248). Unity의 S2 오류 차단은 이 차이를 화면에서 막는 우회책이다.

API의 기억 저장 요청도 아직 예전 방식(카드 순번 선택)이라 저장 v2의 변화 ID·버전 방식과 맞지 않는다(openapi.yaml:259-276). 서버를 시작하려면 복원, 영수증 보존, 탐사 명령의 원자화를 Core에 먼저 넣어야 한다.

고른 카드 대신 다른 카드에 효과가 들어갈 수 있다

중간
